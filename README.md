# orchestrate

`$orchestrate` помогает агенту раздать работу субагентам и оставить себе понимание задачи, решения и приёмку результата.

вы даёте обычную задачу. оркестратор сам определяет, что можно исследовать или делать параллельно, назначает исполнителей, собирает результаты и проводит финальную проверку. выбирать режим работы и вручную распределять роли не нужно.

## кому пригодится

скилл рассчитан на задачи, где есть несколько частей: изучить кодовую базу, найти причину ошибки, реализовать изменение, написать тесты, проверить интерфейс или документацию.

на таких задачах делегирование может сократить время работы и не забивать контекст оркестратора механическими деталями. для маленькой правки он может вызвать одного исполнителя и точечную проверку. запуск нескольких агентов ради одной строки обычно ничего не ускоряет.

## как это работает

оркестратором может быть любая доступная модель. она держит цель, границы задачи, архитектурные решения и критерии готовности. остальную работу она разбивает на части и передаёт субагентам.

каждый субагент получает:

- **цель** — что должно заработать;
- **границы** — какие файлы можно менять;
- **критерии готовности** — как понять, что задача выполнена;
- **проверки** — какие проверки нужно запустить;
- **что не входит в задачу** — куда нельзя лезть;
- **доказательства** — в каком виде вернуть результат и подтверждение проверок.

независимые части запускаются параллельно. если два исполнителя могут изменить один файл, оркестратор разводит их области или запускает последовательно. после реализации свежий проверяющий смотрит на результат отдельно, а оркестратор принимает работу или возвращает её на исправление.

фраза `DONE` ничего не доказывает. оркестратор сверяет изменения, результаты команд, тесты и связь с исходной задачей.

вся координация живёт в сообщениях между агентами. скилл не создаёт планы, журналы, файлы состояния, `.machine/` и другие служебные артефакты. файлы появляются, когда они нужны самой задаче, прямо запрошены пользователем или обязательны по правилам репозитория.

если вы просите TDD, оркестратор сначала получает осмысленный падающий тест, затем передаёт минимальную реализацию и отправляет результат на свежую проверку. тесты, написанные после готовой реализации, он не называет TDD.

## модели в Codex

скилл не привязан к конкретной модели. как стартовую маршрутизацию можно использовать:

- **Astra** как один из вариантов оркестратора для сложной задачи и итоговой проверки;
- **Luna** для недорогого поиска, сбора контекста и ограниченных проверок;
- **Terra** для реализации кода, интерфейсов и задач, где исполнителю нужно принимать локальные решения;
- **Sol** как один из вариантов независимого проверяющего.

это предпочтения, а не жёсткая таблица. оркестратор учитывает задачу, доступность, стоимость и результаты агентов. если нужной модели нет, он назначает те же функции доступным субагентам. проверяющий по возможности не должен быть тем же агентом, который сделал изменение.

## установка

```bash
git clone --depth 1 \
  https://github.com/harnessmachine/codex-orchestrate.git \
  "$HOME/.codex/skills/orchestrate"
```

после установки начните новый диалог или перезапустите Codex, чтобы скилл появился в списке доступных.

## примеры

обычная задача:

```text
$orchestrate найди причину падения авторизации, исправь её и проверь связанный сценарий
```

работа, которую можно распараллелить:

```text
$orchestrate исследуй три варианта миграции API, выбери подходящий и реализуй его
```

TDD:

```text
$orchestrate через TDD добавь защиту от повторного создания заказа
```

ограничения можно указать прямо в запросе: предпочтения по моделям, бюджет, допустимые файлы или запрет на коммит.

## границы

ускорение зависит от того, можно ли разложить задачу на независимые части. последовательная работа с общей точкой изменения часто не выигрывает от параллельного запуска.

скилл задаёт рабочий контракт, но не гарантирует идеальный выбор исполнителя, одинаковое качество разных моделей или наличие конкретных моделей в вашей среде.

вызов `$orchestrate` не расширяет права агента. публикация, деплой, внешние сообщения и другие действия за пределами исходной задачи требуют тех же разрешений, что и без скилла.
